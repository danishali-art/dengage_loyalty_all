## 1. Why

Support staff today can see a customer's balances, one tier panel, tier history and a flat list of postings. They can't answer the questions they get most:

- **"Why did I get this?"** A posting has no visible link to the event, rule or wallet that caused it.
- **"Why didn't I get anything?"** Events that earned nothing, or failed, are invisible in the portal.
- **"Where did my points go?"** A redemption's cash credit or a transfer's counterpart isn't shown next to the debit.
- **"Where am I in my streak / which tier in which program?"** Not shown.

All of this data already exists; it is linked through the event id (`source_event_id`).

## 2. Current state (as-built)

### 2.1 API (`src/dEngage.Loyalty.Api/Customers/`)

| Endpoint | Returns |
|---|---|
| `GET customers` | Contact key, account count, last activity |
| `GET customers/{contactKey}` | Balances (wallet id, name, type, balance, expiration days) + **one** tier progress |
| `GET customers/{contactKey}/ledger` | Id, reason, delta, **account type id**, metadata, date (cursor paging): no event id, no rule, no wallet name, no program |
| `GET customers/{contactKey}/tier-history` | From/to tier, qualifying points, date: no program, no cause |

**Limitations found:**
- **Only one tier is shown.** `CustomersAppService` picks the *first* account that has a tier (`CustomersAppService.cs:74`), so a customer in two programs sees one tier.
- **Activity rows can't be traced** to an event, rule or wallet name.
- **No event, rule-decision, streak, reward or outbound-message view** exists for a customer.

### 2.2 Data available per customer

```
Event  event_inbox (payload, status, error)  [+ contact_key from this CR]
  ├─ Rule decisions   rule_fire_audit (rule, version, conditions + resolution snapshots, delta)
  │    └─ Postings    ledger_entries (wallet, delta, reason, rule) → account type → program
  ├─ Pending          held_postings (delayed rules, not yet released)
  ├─ Streaks          streak_progress (count, completions), streak_log (completion, reward ref)
  ├─ Rewards          reward_log
  ├─ Tier changes     tier_upgrade_log; current tier/lock/grace on customer_accounts
  └─ Messages sent    outbox_events (type, status, attempts)
```

### 2.3 Facts the design relies on (verified)

- **`event_inbox`** holds every event's full envelope (`payload`), status and error, is never purged, is **partitioned by tenant**, and has **no `contact_key` column**. Its key is `(tenant_id, event_id)`.
- **`event_log`** is a narrow per-event row (tenant, event id, contact key, type, occurred time) written by the Consumer for events that carry a `contact_key`. Its only reader is the rule engine's time-window conditions (`TierContextLoader.cs:92`, e.g. "KYC within 1 hour of signup"). It is purged after 12 months by `EventLogRetentionJob`. **This CR does not change it.**
- Per-customer indexes already exist on `customer_accounts`, `tier_upgrade_log` and `reward_log`. **No per-customer index** on `rule_fire_audit`, `outbox_events`, `held_postings`, `streak_log` (leads with campaign) and `streak_progress` (leads with campaign).
- **Per-customer cap usage isn't stored in the database.** `rule_limit_counters` holds per-*rule* budgets only; per-customer limits live in the Redis limit cache.
- **Outbound messages linked to their event:** every outbound type except one carries `source_event_id` in its payload data. **`tier.changed` does not**:
  - a points-driven tier change is keyed `tier_changed:{eventId}:{accountId}`;
  - a reward-driven one is keyed by the streak grant (`tier_changed:streak:{campaign}:{contact}:{completion}:tier_upgrade`), reachable through that event's `streak_log` row;
  - a nightly downgrade has no inbound event at all.

## 3. Proposed direction

### 3.1 Customer header (always visible)

- Contact key (copyable), first seen, last activity, programs the customer is in.
- Chips: tier per program; number of active streaks; number of **failed events in the last 7 days** (red when > 0, always with text: never colour alone).
- No birthday (D2), no complaint action (D3), no test-event action (D10).

### 3.2 Tabs

| Tab | Content | Phase |
|---|---|---|
| **Overview** | One card **per program**: each wallet with balance, **pending** amount (unreleased delayed postings), **expiring soon** amount and date (POINTS wallets with expiry, same FIFO rule as `PointsExpiringDetectorJob`); tier, qualifying points and progress to the next tier, period start, grace end, reward lock date; active streaks with progress bars; last 5 activities. Until P2 the tab shows today's balances, tier progress and tier history. | P2 |
| **Activity** | Every posting: date, **program**, **wallet** (name and type), readable reason, amount, **source** (rule name + version / reward / streak / transfer counterparty / redemption / scheduled job), event type, **eye icon** (§3.4). Birthday-bonus postings appear as normal rows (D2). No running balance (D8). | P1 |
| **Events** | Every event recorded for the customer **from `event_inbox`** (D6): type, occurred, received, processed, status (processed / failed / pending), error, outcome summary (postings count and net amount per wallet), eye icon. Lists events received **after this CR is deployed**. | P1 |
| **Rules & campaigns** | Every rule decision: rule, version, amount, resolution (exclusive winner / stacked / clamped / skipped), conditions snapshot. Per-rule **cap usage** for rules with per-customer limits: today / current period / total **computed from this customer's ledger** for that rule, shown against the cap (D7). | P2 |
| **Streaks** | Each campaign: current count vs target, last period met, completions, status; completion history with what was paid. | P2 |
| **Rewards** | Rewards bought and earned: reward, cost, payout (cash amount and wallet / tier), status. | P2 |
| **Tiers** | Per program: current tier, qualifying points, period, grace end, reward lock; history with **program** and **cause** (points / reward / downgrade, from the `tier_upgrade_log.source_event_id` shape in §2.3). | P2 |
| **Card buckets** | Postings from card-bucket rules (rules with `Template = card_bucket`) and each bucket's per-customer cap usage (computed from the ledger, D7). | P3 |
| **Messages sent** | Outbound events for the customer: type, status (pending / published / failed), attempts, created and published time, dedup key. **No payload** (D5). | P3 |

### 3.3 Filter bar

Laid out like the reference screen (tabs on top, filters in one row, a **Search** button):
- **Program**, **wallet**, **event type**, **status**, **reason group** (earn / burn / transfer / expiry / reward / adjustment), where relevant per tab.
- **Date range** (default **last 30 days**, D9) and **time from / to**, entered in the admin's local time and sent to the API as **UTC** (guardrails §2, Time).
- **Event id** search.
- Results are paged on the server.

### 3.4 Event drawer (eye icon)

Opened from an Activity or Events row:
1. **Wallet(s) involved:** wallet name, type, program, amount, reason. For a posting row, this is the wallet that row hit.
2. **Event:** type, id, occurred / received / processed time, status, error, **payload with sensitive fields masked** (D4).
3. **Why:** for each rule that fired: name, version, conditions snapshot, calculation, resolution (from `rule_fire_audit`).
4. **Everything else this event did:** all postings for this event (a redemption shows the points debit **and** the cash credit; a transfer shows the counterparty's contact key and amount), streak progress or completion, reward bought/earned, tier change.
5. **Messages sent** because of it: type and status (no payload, D5). Linked by `source_event_id` in the message data; `tier.changed` by its dedup key or through the event's streak grant (§2.3).

**Opening any event works**, including events received before deploy: the drawer looks the event up by its id, and the customer's link to it is proven by `event_inbox.contact_key` **or** by the customer's own postings referencing it.

**Postings without an inbound event** (scheduled jobs such as points expiry or the birthday bonus write their own source id) open the drawer with the posting, any rule decisions, and an "Inbound event: none (scheduled job)" note.

### 3.5 Event history (D6)

- **`event_inbox`** gains one nullable column, `contact_key varchar(255)`, and one index, `(tenant_id, contact_key, received_at)`. Nothing else on the table changes: not the key, the other columns, deduplication or partitioning. Partitions inherit the column and index automatically.
- The **Consumer** fills it when it creates the inbox row (`EventConsumerWorker`), from the event data's `contact_key`; it stays null when the event has none.
- **No backfill:** existing rows keep `contact_key` null. The Events tab therefore starts at deploy; Activity and the drawer still reach older events through the customer's postings.
- **`event_log` is not changed**: same role, same 12-month purge.

### 3.6 API (all read-only, tenant-scoped)

Built in the existing `Customers/` resource (`backend-api.md`): routes in `CustomersModule.cs` with `RequireTenantScope`, logic in `CustomersAppService.cs`, records in `CustomersDtos.cs`. List endpoints keep the ledger's existing **cursor paging**. Filters are read from the query string and validated in the app service: `from` ≤ `to`, known `reasonGroup` / `status`, limit within bounds. Bad input returns 400 (`ValidationApiException`).

| Endpoint | Purpose | Phase |
|---|---|---|
| `GET customers/{ck}` (existing) | **P1, additive:** each balance gains `programId` and `programName`, so the portal can fill the program and wallet filters without importing the programs feature. **P2, additive:** per-program overview (wallets with pending and expiring-soon amounts, tier status **per program**, active streaks). The existing single `tierProgress` field stays (frozen, guardrails §2). | P1 / P2 |
| `GET customers/{ck}/ledger` (existing) | **Additive** response fields: `sourceEventId`, `eventType`, `ruleId`, `ruleName`, `ruleVersion` (from the rule-fire audit row for that posting, when present), `accountTypeName`, `accountTypeType`, `programId`, `programName`. **New filters:** `programId`, `reasonGroup`, `from`, `to`, `eventId` (alongside the existing `accountTypeId`, `cursor`, `limit`). | P1 |
| `GET customers/{ck}/events` | The customer's events from `event_inbox` (D6) with filters `eventType`, `status`, `from`, `to`; outcome summary per event. | P1 |
| `GET customers/{ck}/events/{eventId}` | Drawer data (§3.4). Returns **404** (`NotFoundApiException`) unless the event is linked to this customer (its `contact_key`, or the customer's postings). | P1 |
| `GET customers/{ck}/rule-fires` | Rule decisions; filters `ruleId`, `from`, `to`. | P2 |
| `GET customers/{ck}/cap-usage` | Per-customer cap usage computed from the ledger, per rule with per-customer limits (and card buckets in P3). | P2 / P3 |
| `GET customers/{ck}/streaks` | Progress and completion history. | P2 |
| `GET customers/{ck}/rewards` | Reward history. | P2 |
| `GET customers/{ck}/tier-history` (existing) | **Additive:** `programId`, `programName`, `cause`. | P2 |
| `GET customers/{ck}/messages` | Outbound events, no payload; filters `eventType`, `status`, `from`, `to`. | P3 |

**Reason groups** (filter): earn = `earn`, `stamp_earn`, `cash_load`; burn = `points_redeemed`, `points_redeemed_cash`, `reward_purchase`, `cash_spend`, `stamp_reset`; transfer = `transfer_out`, `transfer_in`; expiry = `points_expired`; reward = `reward_cashback`; adjustment = `points_adjusted`, `refund`, `rule_reversal`. Every `LedgerReason` value belongs to exactly one group.

No new error codes reach `DomainErrorTranslator`: everything is raised as typed `ApiException`s in the app service.

### 3.7 Database

- **One migration, `CustomerViewCr1002`** (`backend-schema-shared.md`: CR-suffixed name, generated with `dotnet ef migrations add`, never hand-written):
  - `event_inbox`: new nullable column `contact_key varchar(255)` and index `(tenant_id, contact_key, received_at)`;

- `event_inbox` is partitioned: Postgres adds the column and index to every partition, and future partitions (`provision_tenant.sql`) inherit them; the provisioning script needs no change. No data is changed and no ledger rows are touched.
- `scripts/loyalty_schema.sql` is regenerated with `dotnet ef migrations script --idempotent`; `scripts/loyalty_schema_reference.md` is regenerated by the tool in §3.9.

## 6. Risks

- **Events tab starts at deploy.** Without a backfill, events received before deploy aren't listed in the Events tab; they remain reachable from Activity rows through the drawer.
- **Masking is by field name.** A sensitive value stored under a name outside the agreed list isn't masked. The list lives in one place in the code, so it can be extended.
- **Index build on deploy:** six new indexes, one of them on the partitioned `event_inbox`, built normally (not concurrently); large tables lock briefly during the build. The pre-deploy query below gives row counts so the deploy can be planned.
- **Counterparty display:** a transfer's drawer shows the other customer's contact key, within the same tenant.
- **Message linking edge case:** a reward-driven `tier.changed` is found only through the event's streak grant (§2.3); a downgrade's message has no inbound event and appears only in the Messages sent tab.

Pre-deploy query (read-only):

```sql
SELECT 'event_inbox' AS t, count(*) FROM event_inbox
UNION ALL SELECT 'rule_fire_audit', count(*) FROM rule_fire_audit
UNION ALL SELECT 'outbox_events', count(*) FROM outbox_events
UNION ALL SELECT 'held_postings', count(*) FROM held_postings
UNION ALL SELECT 'streak_log', count(*) FROM streak_log
UNION ALL SELECT 'streak_progress', count(*) FROM streak_progress;
```

## 16. Addendum B — backfill `event_inbox.contact_key` (PROPOSED 2026-10-02, not approved, not implemented)

**Request (developer, 2026-10-02):** add a migration that fills `contact_key` for events received before P1, so the Events tab also lists older events.

**This reverses approved decision D6** ("new events only, no backfill"). D6 was approved by the PO and the Solution Architect, so this is a scope change: **no implementation until the developer confirms both have approved this addendum** (`00-project-guardrails.md` §1).

### B.1 What it would do

One additive data update. No schema change; the column and index already exist. In outline:

```sql
UPDATE event_inbox
SET    contact_key = payload->'Data'->>'contact_key'
WHERE  contact_key IS NULL
  AND  jsonb_typeof(payload->'Data'->'contact_key') = 'string'
  AND  length(payload->'Data'->>'contact_key') BETWEEN 1 AND 255;
```

- **The same rule as the Consumer** (`EventConsumerWorker.InboxContactKey`): a non-empty string of at most 255 characters, read from the stored envelope's `Data.contact_key`. A backfilled row looks exactly like a row the Consumer would have written.
- **Idempotent:** only rows still null are touched, so running it twice changes nothing.
- **No ledger row is touched.** `event_inbox` is not a ledger table, and no other column changes.
- **Down:** a no-op. A backfilled value can't be told apart from one the Consumer wrote; the column itself is dropped by `CustomerViewCr1002`'s Down.

**Dev database today:** 11 inbox rows. **9 would be filled** (`cust_dining_1`, `burn_a`, `burn_c`). **2 would stay null**: they were sent with camelCase `contactKey`, which the engine ignores, so they earned nothing (see B.3, decision B1).

### B.2 Impact

| Area | Change |
|---|---|
| Schema | None |
| Migration | One new data migration (or script, see B2), CR-suffixed, generated shell + hand-written `Sql(...)` |
| API | No contract change. `GET customers/{ck}/events` and the drawer's linkage start covering older events; the header's "failed events (7 days)" can count older failures |
| Portal | Text only: `customers.events.sinceDeploy` / `customers.events.emptyBody` (en + tr) stop saying "since the Customer 360 release" |
| Docs | D6 and §3.5 revised; `docs/SCOPE_BASELINE.md`, `docs/SOW.md` §2.4, `LoyaltySaaSApi.md` ("events received after the CR only" lines) |
| Tests | Postgres E2E: a row with snake_case `contact_key` is filled; a camelCase / missing / over-long one stays null (or per B1); a second run changes nothing; a row on a partition created before the migration is filled |
| Contracts (§2 guardrails) | Tenancy unchanged (the update never crosses tenants; each row keeps its own `tenant_id`); ledger untouched; money untouched |

### B.3 Risks and open decisions

- **B1 — camelCase events.** Leave them null (matches the engine, which never treated them as the customer's), or also read `Data.contactKey`? Reading it would list events the customer earned nothing from. That is useful for support, because it exposes the "camelCase silently ignored" pitfall, but it differs from the Consumer's rule.
- **B2 — delivery and production volume.** `event_inbox` is never purged and is partitioned per tenant. A single `UPDATE` inside an EF migration rewrites every historical row in one transaction: long row locks on rows the Consumer may be touching, large WAL, table bloat until vacuum, and index writes for every row. Options:
  - (a) a single-statement EF migration — simple, fine at dev/test volumes;
  - (b) the migration fills nothing, and a separate idempotent, batched script (`scripts/`, e.g. 10 000 rows per batch per tenant partition, safe to re-run and resume) is run by ops during a quiet window;
  - (c) (a), but per tenant partition, still in one deploy.

  Production row counts are needed to choose. A read-only `SELECT tenant_id, count(*) FROM event_inbox WHERE contact_key IS NULL GROUP BY 1` gives them.
- **Accuracy:** a backfilled event is listed by the contact key the event carried, which is what the engine used. Older events that earned nothing are now listed too, which is intended.

### B.4 Next step

1. The developer confirms PO + Solution Architect approval of this addendum, and answers B1 and B2.
2. Claude Code implements: migration and/or script, tests, the text and doc updates above, and an implementation record here.
