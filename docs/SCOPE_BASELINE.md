Transfer: `maxPerDay` required (`ratio`/`fee` out of scope). The generic engine never posts these rules. Existing redeem/transfer rules disabled by migration `DisableLegacyBurnRulesCr1005` and can't be switched on until completed. Cash rounded down to the cash wallet's decimals. **CR 2026-10-06 D22:** `order.refunded` accepts no rule type (the built-in refund already reverses the order; a Reversal rule there reversed it twice) — existing ones disabled by migration `DisableReversalRulesOnOrderRefundedCr1006` and refused on edit/re-enable (`rule_type_retired`); the engine also skips them. ReversalRule stays for tenant-defined events. **CR 2026-10-06 Part 1b:** rules on `signup` / `kyc.completed` pay each customer once per rule, on every rule, past awards included (D4, D12); every cap follows On breach on exclusive and stackable rules — a cap is never exceeded (D6, D13). **CR 2026-10-06 Phase 2:** a new rule may set only the Configuration / Limits fields that apply to its trigger and type (`RuleFieldCatalog`, served as `applicableFields` by `GET rules/metadata`; 400 `field_not_applicable`); no expiry override on a CASH target; existing rules unchecked (D5) | Done | §2.2 |

| Tiers | Point-threshold ladder, lifetime/periodic qualification, grace period; a tier targeted by an active tier-upgrade reward can't be deleted (`tier_in_use_by_reward`, CR 2026-09-30) | Done | §2.2 |

**Program gating (1.3.CL):** the consumer evaluates a program only when it is **published and active** (`CampaignEvaluationService`, `RuleSyncService`). **CR 2026-10-05 (item 5):** the per-event handlers that post directly — `points.redeem`, `points.transfer`, `reward.purchase` (every reward type), `cash.added`, `cash.spent` — refuse a program that isn't published + active with `program_not_live` (cash events report it with the new `loyalty.cash.add_failed` / `loyalty.cash.spend_failed`). Known remaining gap: `order.refunded` (on purpose) and the ledger/tier jobs don't check program status — see `docs/SOW.md` §3.
